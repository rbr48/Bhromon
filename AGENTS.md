# Bhromon — Agent Memory & Project Playbook

This document serves as the persistent system memory, architectural guidelines, and operating playbook for the Bhromon project. It was compiled from comprehensive multi-session trajectory analysis.

---

## 1. Project Overview & Architecture
- **Repository**: [https://github.com/rbr48/Bhromon](https://github.com/rbr48/Bhromon)
- **Primary Branch**: `main` (active and default).
- **GitHub PR Workflow & Dual-Agent Review Gate (MANDATORY)**:
  1. Never push directly to `main` on GitHub. Always create a feature/fix branch, commit changes, push the branch, and open a Pull Request via GitHub CLI (`gh pr create --base main`) or standard Git/GitHub PR tools.
  2. **Mutual Peer Review Required**: Even when all CI checks are green, NEVER merge any PR to `main` before Antigravity and Claude review each other's PR on GitHub. Mutual peer sign-off must be exchanged and documented in PR comments.
  3. **Green Required CI Checks**: Zero tolerance for failing or in-progress checks on required workflows at merge time (`Dart Format`, `Analyze`, `Build Web (release)`, `Test`, and `Build Android (debug APK)` / Functions / Media Server when triggered). Note: Intentionally skipped jobs (such as `Build iOS (no codesign)`) do not block merge.
- **Product**: Bhromon is one app for every group you belong to: families, offices, campuses, messes, housing societies, savings groups and trips. The name, the Android and iOS identifiers, the domains and the Firebase project are unchanged. Copy and branding follow the group product; a trip is one group type among the others.
- **Tagline & Brand Identity**: Official brand tagline is **"Bhromon — Walk Together"** (Bengali: **"ভ্রমণ — একসাথে পথচলা"**). Secondary positioning statement: *"Walk together through every group: family, mess, campus, office, and shared journeys."* Visual identity uses the iconic 3D green sculptural compass needle / 'B' emblem with 100% transparent background across launcher icons, splash, favicon, and in-app headers, alongside the original vintage wordmark.
- **Architecture**: Clean Architecture (Domain, Data, Presentation) with injectable DI, Drift (SQLite) for offline relational storage, and Hive for encrypted local boxes.
- **State management**: by feature. `tour_group` screens use `StatefulWidget`s that call repositories directly and listen to their streams. BLoC and Cubit remain in the other features. New tour-group code follows the direct pattern; don't add BLoC there.
- **Status**: free and open source, with no business model. No feature is sold, and no paywall or payments should be added. The Game Zone is a core feature and stays.
- **Backend**: Firebase Firestore (with offline persistence), Cloud Functions (TypeScript), Firebase Auth, Firebase Storage, and Firebase Hosting.
- **Live Deployments**:
  - **Flutter Web**: [https://app.bhromon.fun](https://app.bhromon.fun) / [https://bhromon-ff801.web.app](https://bhromon-ff801.web.app)
  - **Android Releases**: Signed release APK (`build/app/outputs/flutter-apk/app-release.apk`) & Play Store App Bundles (`aab`).

## 2. Google Play Store & Android Standards
1. **Target SDK**:
   - Always target **Android 16 (API Level 36)** or higher (`compileSdk 36`, `targetSdk 36`).
2. **Photo & Video Picker Compliance**:
   - Do **NOT** request broad storage permissions `READ_MEDIA_IMAGES` or `READ_MEDIA_VIDEO`.
   - Use the Android system Photo Picker via `image_picker` / system pickers.
3. **Version Numbering**:
   - In `pubspec.yaml`, increment version and version code monotonically on each release (e.g., `1.8.125+179`). Never reuse a version code across builds.
4. **Windows Gradle Build Contention & Directory Locks**:
   - Always keep `org.gradle.vfs.watch=false` in `android/gradle.properties` to avoid Windows directory locks (`AccessDeniedException` during `mergeReleaseNativeLibs` or `packageRelease`).
   - In `android/app/build.gradle`, on Windows only, disable intermediate tasks: `artprofile`, `nativedebugmetadata`, `cleanmergereleaseassets`, `cleanmergereleasenativelibs`, `cleanmergereleasejnilibfolders`, `cleanmergereleaseresources`, and `cleanpackagerelease`. Keep `nativesymboltable` enabled and keep `ndk { debugSymbolLevel 'SYMBOL_TABLE' }`: the release AAB fails to strip native libraries without them.
   - If `AccessDeniedException` occurs during `extractReleaseNativeSymbolTables`, terminate lingering Gradle/Java daemons (`Stop-Process -Name java -Force`) and delete `build/app/intermediates`.
   - Deleting `linux/flutter/ephemeral` and `windows/flutter/ephemeral` resolves symlink deletion locks on Windows during `flutter pub get`.
   - Before running `flutter test`, remove `build\unit_test_assets` if directory deletion locks occur.
5. **Google Play App Signing vs Upload Key (Google Sign-In Error 10 / DEVELOPER_ERROR)**:
   - When Google Play App Signing is enabled, Google Play strips the developer's upload signature and re-signs distributed APKs with Google's managed **App signing key**.
   - Builds installed from Google Play (Production, Open, Closed, or Internal Testing tracks) carry Google's **App signing key** signature, NOT the **Upload key** (`upload_certificate.pem`).
   - If Google Play's **App signing key SHA-1 (and SHA-256) certificate fingerprint** is not registered in Firebase Console (`Project Settings -> General -> Your apps -> com.bhromon.app`) and Google Cloud Console OAuth 2.0 Client IDs, Google Sign-In throws `PlatformException(sign_in_failed, com.google.android.gms.common.api.h: 10: , null, null)` (`CommonStatusCodes.DEVELOPER_ERROR`).
   - Requesting an upload key reset in Google Play Console takes 48 hours to activate and only affects future `.aab` uploads. It does NOT resolve Google Sign-In for Play Store builds; copying the **App signing key SHA-1** into Firebase Console immediately resolves it without requiring a new APK build.
5. **Windows Gradle Build Contention**:
   - Always keep `org.gradle.vfs.watch=false` in `android/gradle.properties` to avoid Windows directory locks (`AccessDeniedException` during `mergeReleaseNativeLibs` or `packageRelease`).
   - In `android/app/build.gradle`, on Windows only, disable intermediate tasks: `artprofile`, `nativedebugmetadata`, `cleanmergereleaseassets`, `cleanmergereleasenativelibs`, `cleanmergereleasejnilibfolders`, `cleanmergereleaseresources`, and `cleanpackagerelease`. Keep `nativesymboltable` enabled and keep `ndk { debugSymbolLevel 'SYMBOL_TABLE' }`: the release AAB fails to strip native libraries without them.
   - Deleting `linux/flutter/ephemeral` and `windows/flutter/ephemeral` resolves symlink deletion locks on Windows during `flutter pub get`.
6. **Windows Cross-Drive Kotlin Compilation Invariant**:
   - The project repository is on drive `E:` (`E:\Projects\Bhromon`) while Flutter's Pub Cache resides on drive `C:` (`C:\Users\USER\AppData\Local\Pub\Cache`).
   - Kotlin incremental compilation can throw `IllegalArgumentException: this and base files have different roots` when computing relative paths across different Windows drive roots.
   - If incremental cache errors occur, set `kotlin.incremental=false` in `android/gradle.properties`.
   - Terminate lingering Gradle/Java daemons (`Stop-Process -Name java -Force`) if build intermediates lock up.
7. **Google Sign-In 7.x Android Credential Manager Invariant (`serverClientId`)**:
   - In `google_sign_in: ^7.x` on Android 14+ (Credential Manager API), calling `GoogleSignIn.instance.initialize()` without `serverClientId` triggers `GetCredentialFailureType.missingServerClientId`, throwing `GoogleSignInExceptionCode.clientConfigurationError` ("serverClientId must be provided on Android").
   - Always supply `serverClientId` (the Web Client ID from `google-services.json`, `client_type: 3`) to `GoogleSignIn.instance.initialize(serverClientId: ...)` before calling `authenticate()`.
8. **Google Play Services Absence Mapping (`google_sign_in_failure.dart`)**:
   - On devices or emulators without Google Play services, Google Sign-In fails with `providerConfigurationError`.
   - `googleSignInFailureReason` maps this error to `AuthFailureReason.googlePlayServices`. The sign-in screen shows the localized message for that reason (`auth_error_google_play_services`) instead of a raw platform exception. The raw error goes to the log.
   - Cancelling the Google account window is `AuthFailureReason.cancelled`: the cubit returns to the sign-in form with no error message.

## 3. Web Compatibility Invariants (`kIsWeb`)
1. **Zero `dart:io` on Web**:
   - Never call `Platform.isAndroid`, `Platform.isWindows`, or `Platform.operatingSystem` directly without guarding with `if (!kIsWeb)`.
2. **Background Services**:
   - Mobile-only background services (`SyncWorker`, `Workmanager`, `flutter_local_notifications`) must be wrapped with `if (!kIsWeb)`.
3. **Web Deployment Protocol**:
   - Build: `flutter build web --release`
   - Deploy: `firebase deploy --only hosting`

## 4. Key Subsystems & Business Logic

### A. Universal Tour Engine
- The app has transitioned from a hardcoded 5-day Cox's Bazar tour to a **Universal Tour Engine** (`lib/features/tour_group/`).
- Supports any destination, duration (e.g., 1-day day tour to multi-week treks), and tour style (Beach, Hill-Trek, Heritage/Cultural, Riverine, Nature/Forest).
- Computes dynamic itineraries, budget estimations, and packing checklists per person/family.
- **Multi-destination trips (`itinerary_models.dart`, `widgets/itinerary/itinerary_editor.dart`):** a tour holds an ordered list of `stops` (Cox's Bazar → Bandarban → Sajek, Sylhet → Sreemangal, ...), each with its own kind, arrive and leave dates, nights and notes. Admins edit them; `saveItinerary` keeps the tour's `destination` summary, tour type and dates in step. Tours saved before stops existed read as one stop with id `main` (`effectiveStops`). `stopOn(date)` tells which stop a day belongs to; expenses and notices use it when no stop is chosen. `destination_catalog.dart` has 40 Bangladesh presets with coordinates (longest name match wins).
- **Route roadmap (`journey_tracker_screen.dart`, `route_engine.dart`):** `RoutePlan.of(group)` turns origin → stops → (optionally) home into legs. Each leg has a transport mode (road, rail, air, river, sea, jeep, boat, trek), a straight-line distance with a per-mode detour factor, an estimated duration, and planned and actual depart and arrive times (`legPlans`, keyed `origin>stopId` with `FieldPath`). Progress, the current and next leg, ETAs and a Google Maps directions link (none when there are more than 9 waypoints) come from the plan. Checkpoints are typed (food, prayer, fuel, washroom, viewpoint, army checkpost, ferry, toll, ...), belong to a leg, and are ticked off as visited; the author or an admin edits them. `route_suggestions.dart` proposes common highway stops from Dhaka. Distances are estimates and are labelled that way.

### B. Tour Group Hub & Trip Ledger
- **Access is membership-based.** `memberships/{tourId}__{email}` decides who can read a tour. Roles are `owner`, `admin` and `member`. Only the owner changes ownership or the invite code, or promotes someone to admin. Nobody adds another person by email: an owner or admin cannot write a membership for someone else, so a person joins only by themselves, with the invite code. Admins edit trip details and remove members; the owner's row cannot be removed.
- **Family circles (`TourGroup.kind`, `GroupKind.family`):** a family circle starts without a trip. It has no dates, destination, seats, tide, journey, quiz, scrapbook or checklist. It keeps Feed, Ledger, Notices, Calendar, Safety, Games, Channels and News. The group tools come from `hubModulesFor` (`domain/services/hub_modules.dart`), which hides the trip-only tiles; the hub's golden test (`test/features/tour_group/hub_modules_golden_test.dart`) pins the result for every type and flag. Any member posts a notice in a family circle that is not an office, a campus, a mess, a housing society or a samity (`hasManagedNotices` in `firestore.rules`), and its author or an admin deletes it. Only a plain family circle with no preset is a household: dependents, the album and family dates are for households alone (`isHouseholdTour` in the rules, `isHousehold` in the app). The family dates tile takes the calendar's place only for a household; any other family-style circle keeps the ordinary calendar (`hub_module_calendar`), and the hub's `calendar` builder checks `isHousehold`, not `isFamily`. Trip rules are unchanged.
- **Shared shopping and to-do list (`family_tasks`, `family_task_daily`; `pages/family_tasks_screen.dart`, `widgets/family/`, `domain/services/family_task_rules.dart`):** a family-style circle that is not an office, a campus or a study circle has one list, with two kinds, to buy and to do (`isSharedListTour` in the rules; the hub tile comes from `hubModulesFor`). A study circle has no list: the hub leaves the tile out, its home card shows no to-do line, and the rules refuse the list and its day counts there. Any active member adds an item under their own email and ticks or unticks it under their own name: a tick writes `doneByEmail` and `doneAt` (server time), and an untick clears both. Only the item's creator or an admin changes its text, kind or assignee, or removes it. The rules refuse any other field, so an edit never changes a tick. A member adds at most 200 items on a Dhaka day (`familyTaskDailyLimit`): the item and the member's counter (`family_task_daily/{email}__{yyyymmdd}`) are written in one batch, and the rules check the count (`familyTaskCounted`), so a refused batch adds nothing. Items carry `createdAt` (server time). An item saved before it existed sorts first among the open items, and an item ticked before `doneAt` existed sorts last among the ticked ones. The list is read in full through one shared stream per circle (`SharedStreamRegistry`, counted by `GroupStreamBudget.familyTasksKey`) with no limit, and the four home cards share it. A list above 500 items says it is long, and the finished items the member may remove can be cleared in batches of 400. A write the server has not confirmed within 8 seconds stays queued, and the screen says it is saved on this phone. A name is the member's name in the circle, or "Former member" once they have left; an address is never shown. The leave purge keeps a leaver's items under the stand-in (`familyTaskOf` in `functions/src/lib/tourContentPlan.ts`), clears the assignments to them, and deletes their day counters; deleting a tour removes both. Offices, campuses and study circles have no list, and trips keep their own checklist. Tests: `functions/tests/family_tasks_rules.test.js` and the family cases in `functions/tests/tour_content_purge.test.js` (on the emulator); `test/features/tour_group/family_task_rules_test.dart`, `family_task_repository_test.dart`, `family_tasks_screen_test.dart` and `family_home_summary_test.dart`.
- **Closing an account (`gdprDeleteUser`, `functions/src/lib/accountTours.ts`, `functions/src/lib/accountErasure.ts`):** the account leaves each tour it is in first. Then it removes what the person owns (trip logs, pins, follows, likes, visits, calls, the messages they sent in direct chats, their storage folder), and the media server removes their files and chat-service data (`POST /purge/account`). Every step can run again, and the CDN is asked to clear the deleted files when `config/cdn` is set. A tour it owns passes to an admin, or else to the longest-standing member; a tour nobody else is in is deleted. Each removed membership triggers `onTourMembershipRemoved`, which purges what the person put into that tour. The account is deleted last, so a failure can be retried.
- **Feed writes are checked by the rules.** A post, comment or story is stamped with `createdAt == request.time` and must be under the caller's own email. Likes and story views change only the caller's own entry (`ownEntryOnly`); comment counts move by one. Post edits are limited to a fixed field list, and the author or an admin makes them. Story votes and reactions are keyed by email with `FieldPath`, never a dotted string, because an email's dots would split it. Story delete: author or admin. Highlights carry `createdByEmail`; the creator or an admin deletes them (highlights saved before this field existed can be removed by admins only). Deleting a post removes its comments first, because their delete rules read the post.
- **Feed paging (`PagedPostFeed`):** the feed is read in pages of 60 by creation time. Each page is a live query over a range (`createdAt < upper`, `>= lower`), and the bounds come from `feedPageBoundary`. Adding or deleting a post shows at once, and the pages never overlap or leave a gap. `functions/tests/paged_feed.test.js` checks the same queries on the emulator.
- **Invite codes** live in `invites/{code}`: readable by exact code, never listed. Codes are 8 characters from an unambiguous alphabet (six-character codes from before are retired; `functions/scripts/upgradeLegacyInviteCodes.js` gives their tours new codes, dry run first). Joining always creates a plain member and is refused for accounts in `tours/{id}/bans`. Removing a member writes a ban and deletes the row together.
- **Join by QR code (`invite_qr_code.dart`, `group_qr_sheet.dart`, `join_by_qr_screen.dart`, `invite_join_link.dart`):** every member, owner and admin included, opens the group's QR code from the group menu (Join QR code) and shares the picture (saved on the web) or copies the link. The code holds only `https://app.bhromon.fun/#/join?code=CODE` with the group's current invite code, so a renewed code changes the picture; it carries no name or member list. The scanner is the title-bar icon on the Groups list, placed before the Play Store link on the web and before the language button on a phone. It reads a QR code with the camera (`mobile_scanner` 7.5; on the web the plugin loads zxing-wasm from jsDelivr at a pinned version) or a pasted link or code. Only a bare code or a join link on `app.bhromon.fun` is accepted (`inviteCodeFromScan`), and a valid one opens `/join/CODE`, where the person still confirms before joining. Android's minimum SDK comes from Flutter (24), above the plugin's 23. Tests: `test/features/tour_group/domain/services/invite_join_link_test.dart`, `test/features/tour_group/presentation/pages/join_by_qr_screen_test.dart`, `test/features/tour_group/presentation/widgets/invite_qr_code_test.dart` and `test/features/tour_group/presentation/widgets/group_qr_sheet_test.dart`.
- **Rules are tested on the emulator:** `functions/tests/tour_group_rules.test.js`, `tour_group_storage_rules.test.js` and `firestore.rules.test.js` all share one emulator project. Run them with `npx firebase-tools@13.35.1 emulators:exec --only firestore,storage,auth --project bhromon-rules-test-project "cd functions && npx jest --runInBand tests/"`. `--runInBand` is required because the suites clear that project. Storage rules look up memberships on the emulator's `--project`, so the flag must name that project. The CLI is pinned: firebase-tools 15.x fails the Storage rules' firestore lookups, which denies every upload.
- **Expense allocation (`trip_ledger_engine.dart`):** always integer paisa. User amounts go through `parseTakaInput` (Bengali digits accepted; zero, negative and over-cap amounts refused). An expense's `splitMode` is `family` (the default and the only mode before this field: participants weighted by `familyCount`, 1 to 20, which members set for themselves), `equal`, `exact` (paisa per email in `splitShares`, which must add up) or `shares` (parts per email). An exact amount owed by someone who has left is spread over the rest so the books balance. Payers and depositors who have left keep their balance; email matching ignores case.
- **Fund (`expense_ledger_screen.dart`, `fund_analytics.dart`, `widgets/fund/`):** tabs Overview, Expenses, Settle up, People, Deposits. Settle-up payments live in `tours/{id}/transfers` (a null `fromId` is the fund paying out, a null `toId` is money into the fund); they move balances and the fund (`net = contributed + sent − received − share`). The rules let a member record only a payment they made or received, admins any; payments are never edited, and the author or an admin deletes them. Suggested settlements carry member ids so "Mark paid" records the right people. Admins set `fundBudget` on the tour (budget per category plus a per-person collection target, multiplied by each member's `familyCount`). `FundReport` gives budget lines, the daily burn and projection, the collection and who still owes, and spending by stop, by day and the largest expenses. A foreign-currency expense keeps `currency`, `originalMinor` and `fxRate`; the books use the BDT amount. The CSV export is UTF-8 with a BOM.

- **MFS payments (`mfs_sms_parser.dart`, `mfs_settlement_sheet.dart`, `monthly_ledger_pdf.dart`, `expense_models.dart`):** an expense or settlement can carry `mfsInfo` (provider, TrxID, masked numbers, fee, verification status). Members record their own payments as `unverified`; a tour admin verifies or disputes them, and the rules check each transition. Once verified or disputed, a record is frozen for members. A settlement is `tours/{id}/settlements/{settlementId}`. The per-group TrxID registry, `tours/{id}/mfs_trx_registry/{trxId}`, is atomically filled upon settlement or expense recording (`addSettlement`, `addExpenseWithSplit`) to prevent duplicate TrxID reuse. `TripLedgerEngine.computeMonthlyStatement` carries balances forward month to month and gives a verification digest. The settlement sheet (`MfsSettlementSheet`) and monthly PDF statement (`exportMonthlyLedgerPdf`) are linked directly from the ledger overview top action bar. Payments are still never edited, so the rules do not let an admin change a transfer's `mfsInfo`.
- **Offline:** the tour list comes from memberships, not the cache, so tours the user left stop showing. A write that is not acknowledged within 8 seconds is reported as syncing and kept queued; a rejected write is removed from the local cache.
- **Safety alerts (SOS):** only a trip, a household (a family circle with no preset), a mess and a housing society have SOS. Every other group has none: no SOS row, no Family Safety hub, no alert banner, and no alert in the rules, the export or the VPS. The rule is `TourGroup.supportsSafetyAlerts` in the app, `sosAllowedTour` in `firestore.rules` and `sos_policy.py` on the VPS; keep the three in step, and test it in `test/features/tour_group/sos_policy_test.dart`, `functions/tests/tour_group_rules.test.js` ("which groups have SOS") and `media-server/tests/test_sos_push.py`. An alert is raised by pressing and holding the button for two seconds (`HoldToToggleButton`), not by a tap. Its sender's own position is read first, for three seconds at most, and sent with it. Only the sender may raise under their own email. Each alert field is checked by type in the rules, and the app reads each alert separately, so one bad document cannot hide the others. Turning the siren off always closes the alert, even when it has not reached the server yet. Leaving the screen does not end the alert: an own open alert within six hours turns the siren back on when the screen opens, so the siren follows the server. The six-hour window is applied in the app and closes an own alert that is still open after it. Resolving may change only the resolution fields. The members' push is sent by the VPS watcher (`on_sos_snapshot`) and by `POST /notify/sos`, which pushes only the caller's own open, recent alert in a tour with SOS; each alert is pushed once (`push_claims`), and a sender's alerts push once per two minutes. The push is sent under the sender's name in the group (the membership's `displayName`), on the `bhromon_sos` Android channel, time-sensitive on iPhone, and it is followed by an "ended" notice when the alert closes, which replaces the alert on the phone. A push is sent to every device a member has signed in on. A member who has never signed in on a device gets no push, and the family's text messages (`emergencySmsUri`) are offered when an alert has not reached the server. Alerts also show in the app.
- **Office & Team (`preset: 'office'`):** an office or team is a family-style circle (`kind: family`) with `TourGroup.preset` set to `office` (`isOffice`). It drops the household tiles (dependents, album, family dates, shopping & to-do) and Safety. Only admins post notices (`hasManagedNotices` in `firestore.rules`), and members answer them. The rules refuse dependents, shopping and to-do items and family dates in an office or campus (`isHouseholdTour` and `isSharedListTour`). An owner or admin can turn Moments off (`momentsEnabled`, the hub's group menu); while it is off, posts and stories are refused (`momentsOpen` in `firestore.rules`) and the Moments tile and camera button are hidden. The ledger offers office categories (`kOfficeExpenseCategories`), and a lunch or tea shortcut opens the expense editor with the title and category filled in. The answer sheet (progress, waiting list, share) is the reminder; answer reminders are pushed by the media server (see Answer reminders).
- **Campus & Batch (`preset: 'campus'`):** the office rules with campus copy. Admins post routine notices, members answer them, and Moments stays on unless an admin turns it off (see the Moments setting). The ledger offers campus categories (`kCampusExpenseCategories`), and a snacks or tea shortcut opens the expense editor with the title and category filled in. The channels are named Canteen & tea and Events & picnic. `TourGroup.isManaged` and `isManagedTour` in the rules cover both presets.
- **Mess & shared home (`preset: 'mess'`):** a family-style circle for a shared meal arrangement or a shared flat. Its owner and admins post the notices and members answer them (`hasManagedNotices`). It drops dependents, album and family dates (`isHouseholdTour` leaves it out), and keeps the shared shopping and to-do list (`isSharedListTour`), Safety and SOS. Members log their own breakfast, lunch and dinner for each day (0 to 5 each), and an owner or admin may log for anyone; a row lives at `tours/{id}/meals/{dateKey}__{email}`, and only a mess keeps them (`isMessTour`). The ledger offers mess categories (`kMessExpenseCategories`) and a bazar shortcut that opens split by this month's meal totals (`mealTotalsForMonth`), so a member with no meals gets no share. Dates and totals are in `meal_engine.dart`. The channels are named Kitchen & menu and Bills & chores. `TourGroup.isMess` marks the preset; `isManaged` does not include it, but `hasManagedNotices` does.
- **Housing society (`preset: 'society'`):** a family-style circle for an apartment building or housing society. The owner and admins post the notices and members answer them (`hasManagedNotices`). It drops dependents, album and family dates, and keeps the shared shopping and to-do list, Safety and SOS. Residents raise service requests in `tours/{id}/service_requests` (`service_request_models.dart`, `service_request_rules.dart`, `society_requests_screen.dart`): a request starts open under the resident's own email, and only its author may correct the words while it is open. The owner or an admin moves it to in progress or resolved with a note for the residents (`status`, `adminNote`); the author or an admin removes it. The ledger offers upkeep categories (`kSocietyExpenseCategories`), a chat `/split` in the maintenance channel books to Repairs, and the channels are named Maintenance and Meetings & events. A resolved request can be booked to the ledger: the committee's button opens the expense editor with the request's title and the Repairs category.
- **Rotating savings group (`preset: 'samity'`):** a samity records a rotating savings scheme; the app keeps the schedule and the records and moves no money. The schedule is `SamityConfig` on the tour document under `samity` (`samity_models.dart`): what each member pays per cycle, the first month as yyyy-MM, the due day from 1 to 28, and the payout order by email. There is one cycle per member, each member takes the pot once, and the pot is the contribution times the members in the rotation. A payment is `tours/{id}/samity_payments/{cycleKey}__{email}`: a member records their own and an owner or admin records anyone's; the amount is what has been paid so far for that cycle, at most the contribution. A handover is `tours/{id}/samity_payouts/{cycleKey}`, written by an owner or admin only. `SamityLedger` (`samity_engine.dart`) gives each cycle's status (upcoming, due, overdue, collected, paid out), the current cycle, the next payout and what each member owes across the cycles that have fallen due, each cycle counted on its own. Only an owner or admin changes the schedule, and the rules check its shape (`validSamityConfig`). Its notices are managed like a society's, and it keeps the shared list. It has no Safety hub and no SOS.
- **Study or book club (`preset: 'study'`):** a family-style circle with subjects, a shared book list and a reading plan, and any member can post notices. Subjects (`tours/{id}/study_subjects`) follow the book approval: an admin adds one and it is listed at once, and a member proposes it for an admin to list or decline with a note. Each subject has its own modules (`study_subjects/{id}/modules/{key}`). Every module is live, and none is listed as coming soon: an admin turns a module on, renames it, and sets who may post (`members`, `admins`, or `approval`, where an admin shows each post or assignment first). Assignments read through the rules: a member reads the shown ones and their own waiting ones, and an admin reads all (`assignments` read rule); the app runs one query for each part of a member's list and merges them (`watchStudyAssignments`). The Today card shows the nearest assignment due today or within three days that the viewer has not finished (`nextDueAssignment`, `TodayCardLine.assignment`). The group calendar marks each day an assignment is due and lists the next five (`loadStudyAssignments`, `assignmentDueDays`, `upcomingStudyAssignments`). ### C. Tour Reels & Media Sharing (VPS Microservice)
- Vertical reels video feed (`tour_instafeed_screen.dart`) matching Family Bhromon with video playback controls, aspect ratio fitting, upload flows, and media filters.
- **Dedicated VPS Media Storage**: To bypass Firebase Storage rate limits and bandwidth charges, media is hosted on the user's Hostinger VPS (`bhromon.fun`) in an isolated Docker container (`bhromon-media-app` on `127.0.0.1:8210`), saving to `/var/www/bhromon-media`.
- **High-Performance Streaming**: Nginx serves `/media/` using `http_mp4_module` with native HTTP Range Requests (`206 Partial Content`) for instant video reels seeking.
- **Private media**: tour, chat and profile media is served only with a signed link (`?u=<uid>&s=<signature>`). The app gets its key from `POST /api/media/access-key` after sign-in and signs each `/media/` URL with `signedMediaUrl` (`lib/core/media/`). nginx asks `/internal/media-auth` (`media-server/media_access.py`) before it serves a file, and that check applies membership. `MEDIA_ACCESS_ENFORCE` turns refusals on, and stays 0 until the app that signs links is released (see `media-server/README.md`, "Private media links"). Responses are `Cache-Control: private`, so shared caches never keep a file.
- **Moments & Media Server Quotas (PR #175)**:
  - Resharing a post to a story creates a hard link on the server (`POST /api/media/copy`), decoupling deletes between posts and stories. Every delete verifies no other post, story or highlight references the file before unlinking.
  - Media quotas: 20 GiB per tour, 4 GiB per user per tour, 5 GiB host free-disk floor, and 60 uploads/min rate limit per user.
  - Daily cleanup: Scheduled daily job (04:00 Dhaka) purges stories older than 24h and unreferenced media files, and call records (`calls/{id}` with their ICE candidates) older than 30 days (`media-server/call_cleanup.py`).
  - LikeState: Optimistic like state manager prevents like removal on double tap and absorbs rapid-tap network latency.
  - Family-date reminders: Executed directly on media server (`family_dates.py`), eliminating external cloud function timeouts.
- **Uploads go through `TourMediaUploader`**: Uses `Dio` for chunked streaming upload (`POST https://bhromon.fun/api/media/upload`), cancellation via `CancelToken`, real-time progress stream, and deletion via `DELETE https://bhromon.fun/api/media/media/{tourId}/{folder}/{filename}` (with backward-compatible deletion fallback for legacy Firebase Storage URLs). Every request carries the signed-in member's Firebase ID token as a bearer token; there is no shared upload key in the app. The client picks the 32-hex `objectId`, so the URL is known before the response arrives. Limits: images 10 MB, videos 100 MB, reels 3 minutes.
- **Media server (`media-server/main.py`, v2):** checks the ID token and an active membership for every upload and delete. Deletes are allowed for the uploader (recorded in a sidecar under `MEDIA_META_ROOT`), a tour owner, or an admin. Folders and extensions are allowlisted; uploads never overwrite (`409`). There is no shared upload key, and an old build that still sends one is refused. A chat space (`chat_{uidA}_{uidB}`) takes media only from its two people while they share a tour, and a user space (`user_{uid}`) only from its owner. `POST /purge/account` (key-protected) removes a closing person's files and chat-service data, and `backup_store.py` copies the databases and metadata. Run its tests with `cd media-server && pip install -r requirements-dev.txt && pytest`.

### D. Game Zone (`lib/features/game_zone/`)
Game rules live in pure-Dart models/engines (unit-tested); screens only render and drive timers.
Every game screen locks portrait (`common/game_zone_portrait_lock.dart`), keeps its game in a
static session while the user visits other screens, and asks before discarding a game in progress.
1. **Card 29 (`card29/`, model `card29_game.dart`)**:
   - 32 cards (J:3, 9:2, A:1, 10:1, K:0, Q:0, 8:0, 7:0) + 1 for the last trick = 29.
   - Bidding 16–28 from the dealer's left, a pass is final, dealer rotates; all-pass → dealer plays at 16.
   - Strict trump rule with partnership immunity: once trump is revealed, any player who cannot follow lead suit MUST play trump if held when an opponent is winning the trick; if their partner is already winning, they are not forced to trump and may discard or feed points. The bidder reveals trump by playing it while void and may not lead the hidden trump suit; a trump-suit discard before the reveal has no trump power (PlayedCard.trumpEligible).
   - Pair (royalty, K+Q of trump, after reveal): bidding team target −4 (min 16), opponents' pair → target +4 (max 28). Bots claim it too.
   - A finished trick sits in `Card29Phase.trickComplete` until `resolveTrick()`, so no card can be played during the pause.
   - 6-pip match game tracking; a new round after `matchOver` starts a fresh match.
2. **Travel Chess AI (`chess/`)**:
   - Complete Kingside (`O-O`) and Queenside (`O-O-O`) castling (needs the own rook on its corner; moving or capturing on a corner revokes the right).
   - En Passant capture logic; search uses exact make/unmake (`_doMove`/`_undoRecord`), never ad-hoc board edits.
   - Interactive promotion selector modal (Queen, Rook, Bishop, Knight); dismissing it cancels the move.
   - King check visual alert and halo highlight.
   - Move history with SAN notation and Takeback (`undoMove()` restores castling rights, en passant and clocks).
   - Draws: stalemate, insufficient material, 50-move rule, threefold repetition, draw offer; resign.
   - AI (negamax + alpha-beta + quiescence) runs via `compute(chessAiWorker, ChessAiRequest(...))`; depths Easy 1 / Medium 2 / Hard 4.
   - Board coordinate annotations (`a-h`, `1-8`) and last-move highlights.
   - Crisp vector Staunton pawns (_ChessPawnPainter) immune to Android NotoColorEmoji font fallback hijacking, guaranteeing authentic side colors.
3. **Ludo Express (`ludo/`)**:
   - Home tokens remain docked and visible inside central home triangles.
   - Tokens sharing a square split it as a 2×2 grid.
   - Three consecutive sixes forfeits the turn; the counter resets on every turn change (`passTurn()`).
   - Pass & Play mode supporting any combination of Human and Bot players (at least one human); any mode change restarts the turn flow.
   - Board grid is 6:3:6 in every band; track cells are outlined, start squares tinted, safe squares starred.
4. **Teen Patti (`teen_patti/`, model `teen_patti_game.dart`)**:
   - Ranking: Trail > Pure sequence > Sequence > Colour > Pair > High card; A-K-Q is the top run, A-2-3 the lowest.
   - Sideshow (Back-Ask): a seen player asks the previous seen player to compare privately; the target may decline; a tie packs the asker.
   - Dynamic bet raising up to 40 base / 80 chaal; every stake checks the player's chips first (no negative balances).
   - Blind turn limit (max 4).
   - Show ties split the pot between the tied players only; the pot is cleared on payout; pot limit 1280 forces a show.
   - Real-time hand rank badge for seen cards.
   - Chip rebuy popup (+500 chips) when you can't cover boot + one blind.
5. **Carrom (`carrom/`, physics `carrom_engine.dart`, rules `carrom_game.dart`)**:
   - Deterministic fixed-step physics (1/480 s) on a 0..1 board with ICF proportions: friction, cushion and coin restitution, a striker ~2.6× a coin's mass, 4 corner pockets.
   - You play white from the bottom baseline; the opponent (bot or Pass & Play) plays black from the top. Striker slides along the baseline (drag or slider) and may not touch a coin; drag back anywhere and release to shoot.
   - Own coin pocketed → shoot again; opponent-colour coins stay down and count for the opponent.
   - Strict ICF fouls: striker pocketed, own last coin before the queen is covered (including covering her with it in the same shot), or the opponent's last coin. On a foul the shot's own coins, the queen and the opponent's last coin return, one penalty coin is paid and the turn ends; with nothing to pay the penalty is due (`penaltyDue`) and taken from the next coin pocketed.
   - Queen only after an own coin; must be covered on the same or next shot or she returns.
   - First to 9 coins wins the board: 1 point per opponent coin left, +3 for covering the queen.
   - Bot (`CarromBot`) builds cut shots from ghost-ball geometry with the minimum power that carries the coin (friction + momentum transfer), simulates each candidate, and adds aim noise per difficulty (Easy 0.035 / Medium 0.018 / Hard 0.008 rad). It runs via `compute(carromBotWorker, ...)`.

### F. Realtime Calling & WebRTC Voice Lounge Architecture
- **Direct 1-on-1 Calling (`CallSignalingService`, `call_screen.dart`)**:
  - Audio and video calling initiated directly from tour group channel members sheet and direct chat.
  - **Contact is limited to a shared tour (privacy invariant).** A chat, a message, a call, or a chat notice exists only between two active members of one tour. Chat and call documents carry `sharedTourId` and a uid-to-email map (`memberEmails`). The rules check both emails' memberships in that tour, and each membership's `uid` is written only by its own person (`uidIsOwners`), so no one can claim a uid they do not own. The VPS (`media-server/chat.py`) enforces the same check on messages, typing, read receipts, online status, and call signals, through `shares_group` (`main.py`).
  - **Delivery receipts and retries (`message_receipts.dart`, `chat_delivery_receipts.dart`, `media-server/chat.py`).** A message carries the sender's id for it (`clientMessageId`, the Firestore message id). The VPS saves a repeat from the same sender with the same id once: the repeat gets the saved message back (`duplicate: true`) and is not broadcast or pushed again (`save_message_once`, unique index on `(sender_id, client_id)`). Receipts move `pending → sent → delivered → read` and never backwards (`advanceReceipt`). The recipient's phone moves a message from `sent` to `delivered` when the WebSocket delivers it, and only then; a message the recipient has not received stays at `sent`. A `delivered` write from the recipient's side is allowed by `firestore.rules` for the receipt fields only.
  - **Share intake (`lib/features/share_intake/`, Android only).** Files another app shares into Bhromon reach `MainActivity.kt`, which copies each one into `cacheDir/shared_inbox` before it returns, because the other app's read permission ends with the activity. It then tells Dart on `com.bhromon.app/share_intake`. `ShareIntakeHost`, above the navigator, takes them only while someone is signed in and opens a sheet of destinations: a chat (the chat's own send path, through `/chat/:chatId` with `sharedFiles`) or a group channel (`ChannelShareSender`, which uses the channel's uploads). Every type the uploader accepts is offered, within the limit for its kind (`media_rules.dart`, the same limits the server enforces). A text-only share shows a note, because text cannot be sent yet. The manifest accepts `*/*`, so a text-only share also opens the app. iOS has no share target.
  - **Chat page (`chat_screen.dart`).** A one-to-one chat is a single page of messages. Voice and video calls start from the buttons in its header, and the call history with the person is in the chats list's Calls section. Swipe-to-reply on a bubble never starts a call, sends, deletes or marks anything.
  - No directory of people: `users` and `explorer_profiles` cannot be listed (profiles open by user ID only), and `trip_logs`, `archived_trip_logs`, `pro_tips`, `location_pins` lists, `follows`, `likes`, and `pin_visits` are owner- or admin-only. The Start Conversation sheet lists members of the user's own tours (`groupContacts`, `lib/features/tour_group/domain/services/group_contacts.dart`). The legacy social routes (`/map`, `/feed`, `/discover`, `/leaderboard`, `/dashboard`, `/challenges`, `/ar`, `/editor`) are removed from the router.
  - Direct chats made before tours tied them are deleted by `functions/scripts/deleteLegacyChats.js` (Firestore, dry run by default) and by `media-server/delete_chat_history.py` (the VPS database, dry run by default).
  - **A chat's messages listener is opened again once the chat exists (`chat_screen.dart`, `domain/chat_messages_listener_state.dart`).** The rules refuse a chat's messages until its chat document exists, and Firestore closes a listener that was refused, for good. A new chat's first send therefore opens the listener again when the server confirms the write to the chat document (`_ensureChatDocument`). The other person's screen does the same when the chat document first appears on the server in its own listener; a snapshot that only reflects a local pending write does not count. `functions/tests/chat_listener_rules.test.js` pins the rules facts this relies on.
  - Hybrid signaling: Instant VPS WebSocket relay (<15ms) backed by Firestore `calls/{callId}` fallback.
  - **ICE Candidate Queuing (MANDATORY)**: Early ICE candidates that arrive over WebSocket or Firestore before `setRemoteDescription` completes are collected in `_pendingIceCandidates` and drained immediately upon remote description stabilization. This prevents dropped candidates and silent audio failure.
  - **Native Remote Stream Binding**: Always bind genuine WebRTC remote stream (`event.streams.first`) directly to remote renderer with all tracks enabled; avoid wrapping in dummy local media streams.
  - **Audio Session Release (MANDATORY)**: Dispose every `RTCPeerConnection` after closing it. The plugin hands the Android audio mode back only when the last connection is disposed, so `close()` alone leaves the volume keys on the call stream. A setup that never created a connection calls `CallAudioSession.release()`.
  - **Rebuilding a Dropped Link**: Only the caller makes offers. A rebuild is `reoffer` (an ICE restart) answered by `reanswer`, and a callee that notices the drop sends `renegotiate`. These carry SDP over the relay only, because the call document's offer and answer are fixed once written. A callee offer would collide with the caller's, so keep the caller as the only offerer.
  - **Call Log Writer**: A finished call is written to the chat once, by the side whose call-document update succeeds, with the connected seconds from `CallSignalingService.connectedSeconds`. Read the peer uid before `_releaseResources()`, which clears it.
  - **Continuous Audio Sink**: Audio calls and Voice Lounge must keep an invisible 1x1 `RTCVideoView` mounted in the widget tree so WebRTC audio flows reliably on Web DOM and mobile audio sinks.
  - **Mobile Audio Routing & In-Call Controls**: Call `Helper.setSpeakerphoneOn` upon `getUserMedia`, `onRemoteStream`, `onCallStateChange == 'answered'`, and speaker toggling to lock Android `MODE_IN_COMMUNICATION` routing properly. The in-call loudspeaker button routes hands-free audio through the phone's speakerphone cleanly, and the camera switch button in the in-call bottom controls flips between front and back camera dynamically without tearing down the audio track or renegotiating SDP (`614393b`, PR #280). After a call connects, the call screen reads the phone's route 1.5 s later (`CallAudioSession.routeSnapshot`, `readSpeakerRoute`). When the speaker is on and the route did not take, it applies the route once more; the outcome goes to the `call_speaker` Crashlytics key, with `call_system` for calls held by the phone's own call system, and a route that still did not take is also recorded as a non-fatal.
  - **Push End-Call Race Condition Immunity**: A call answered on one device dispatches a push notification to cancel ringing on other devices; in-call signaling ensures an answered call is never prematurely severed by its own ring-cancellation push (PR #274).
  - **Chats List Swipe Navigation**: Users can horizontally swipe between the Chats and Calls tabs cleanly (`514e776`).
  - **Chats list order (`domain/chat_list_sort.dart`, `widgets/chat_list_sort_button.dart`)**: the one-to-one list opens on the newest message first (`ChatListSort.recent`; a chat with no message time goes last). The sort control at the end of the chip row switches to name order (A to Z by the name the chat stores; a chat with no stored name goes last). Both the server list and the offline list go through `sortChatRows`, so they cannot disagree. The choice is not kept between visits.
  - **Calls Tab Query Rules Compatibility**: Firestore rules evaluate list queries against callerId or calleeId equality filters, which an `arrayContains` filter on `participants` cannot prove. The Calls tab reads separate caller and callee queries and merges them client-side via `mergeLatestLists` (`call_history_stream.dart`), sorted newest first.
  - **Bidirectional Negotiation**: Pass `{ 'offerToReceiveAudio': 1, 'offerToReceiveVideo': 1 }` to every `createOffer` and `createAnswer`, voice calls included.
  - **Voice to video**: a voice call negotiates a video section too (the caller adds a send-receive video transceiver; the callee opens it with `_allowVideoUpgrade`), so `startCamera` turns a camera on with `replaceTrack` and no new offer. Each side tells the other whether its camera is on with the relay signal `camera` (`{'on': bool}`), and the call screen shows the other side's video only while it is on. An Android video call shrinks into picture-in-picture when the user leaves the app (`setPipAllowed`).
  - **Phone call system**: a call answered on the native ring screen stays in the phone's call system (Telecom on Android, CallKit on iOS) until it ends, and an outgoing call is registered there with `SystemCallBridge.startOutgoing`. The phone's hang-up, mute and hold (an ordinary call arriving) reach the call through `ActiveCallControls`. Such calls use the plugin's own in-call service, not `CallOngoingService`.
  - **Call waiting**: a call that arrives during a call rings without a ringtone; End & answer hangs up the current call first. In the background the phone's own screen shows it.
  - **Audio output**: with Bluetooth or headphones connected, the speaker button lists the outputs (`Helper.audiooutputs`, `audioOutputKind`), and a picked one stays picked through routing changes.
  - **Cancelled setup (MANDATORY)**: hanging up or leaving the call screen sets `_cancelled` (`endCall`, `dispose`). `_begin` refuses to start a cancelled call, and a camera, microphone or peer connection that finishes opening after the hang-up is closed at once. The call screen starts its setup after the first frame and re-checks `mounted` after each permission prompt.
  - **Ring only what still rings**: a push (background handler in `main.dart`) or relay offer rings only when `CallSignalingService.isStillRinging` finds the call document still `calling` and young. A call left `calling` by a caller whose app went away is closed by the callee's app as `ended` and logged as missed (`expireStaleCall`), never as declined. The VPS watcher sends `end_call` when a call is answered, declined, missed or ended, so the callee's other phones stop ringing; a foreground app closes the ring and shows no banner for it.
  - **Accept on a closed or locked phone**: the phone marks a call answered the moment Accept is tapped and opens the app with the plugin's accept action, but the Accept event is lost when nothing in Dart listens yet. `CallNotificationService` reads `FlutterCallkitIncoming.activeCalls()` on start-up and on every resume (`acceptedSystemCalls`) and answers an accepted call that is still ringing, or closes one that is over. `MainActivity` shows over the lock screen from `onCreate` and `onNewIntent` for that action, until the call screen takes over or Dart finds no call (`releaseAcceptLaunch`).
  - **Call log for a new chat**: `CallLogRepository.record` writes without the tour first; if the chat does not exist yet and the rules refuse, it writes again with `sharedTourId` and `memberEmails`, which open the chat.
  - **Link quality**: loss is measured per poll interval (`PacketLossMeter`), not over the whole call, so the badge and the video bitrate cap recover with the link. The rebuild budget (three) starts again after a link has stayed up for a minute. Candidates held during a rebuild are applied only by the path that applies the new description.
  - **Background calls**: Android runs `CallOngoingService` (foreground service, microphone, plus camera on a video call) while a call is up, started through the `com.bhromon.app/call_audio` channel (`startOngoing`/`stopOngoing`). Its notification has a Hang up button, which ends the call through `CallAudioSession.setHangUpHandler`. While the call screen is open it shows over the lock screen and turns the display on (`showOverLockScreen`), so a call answered on a locked phone opens without unlocking. On the earpiece of an audio call the proximity sensor turns the screen off (`setProximityScreenOff`). iOS declares the `audio` and `remote-notification` background modes. iOS rings a closed app through PushKit (`AppDelegate.swift`): the app registers its VoIP token as platform `ios-voip`, and the media server sends offers to it through Apple (`voip_push.py`) once the APNs key is configured (see `media-server/README.md`).
- **Discord-Style Group Voice Lounge (`VoiceRoomService`, `voice_room_screen.dart`, `group_channels_screen.dart`)**:
  - Drop-in / drop-out group voice channels backed by WebRTC multi-peer mesh with per-peer candidate queuing.
  - Active participants track their presence in Firestore at `tours/{tourId}/channels/{channelId}/participants/{email}` with heartbeat timestamps and mute states.
  - Persistent floating docked voice bar allows users to browse itineraries, chat, or ledger while staying connected in the voice lounge.
  - A connection is kept only while it is still wanted (`_stillWanted`: the room, this side's join and the peer's join all unchanged). A peer who leaves or joins again while a connection is being made has it closed, and a new join is tried. Each side deletes the ICE candidates it wrote when a connection closes.
- **STUN/TURN Infrastructure (`sotto-coturn-1`)**:
  - Running on Hostinger VPS (`coturn/coturn:4.18.0`) to relay media when direct peer-to-peer UDP is blocked by symmetric NATs or restrictive mobile carrier firewalls. There is no third-party TURN fallback: `CallIceConfig` asks the server twice, keeps the last credential until it expires, and only then falls back to STUN. The relay host is `turn.sottocall.com` (`TURN_SERVER_HOST`): TURN on UDP and TCP 3478 and TLS on 5349 (`turns:`). coturn's certificate matches that host (`turn.sottocall.com`). `TURN_TLS_URLS` adds more TLS addresses, such as 443 for networks that allow only HTTPS (see `media-server/README.md`).

### I. Local Encrypted Storage (Hive, `HiveEncryptionService`)
- **Boxes open through `openEncryptedBox`** (`lib/core/security/hive_encryption_service.dart`), with the device key kept in the platform keystore. The fixed key that older versions fell back to is only ever read, to move a box to the device key. Without a device key, boxes live in memory for the session and nothing is written to disk.
- **A box is checked before it is opened.** The device key must read it, or an older key must, and then its entries move to the device key. Native checks a copy of the file and web checks the box in IndexedDB; a box the device key opened last time (`hive_key_marks`) opens directly on both. Hive lower-cases box names, and the service looks for the same files. A box that no known key can read (a wrong key, or a damaged file) is recreated empty under the device key. Any other failure (a file that cannot be read, a folder in the way, a storage error) throws to the caller and leaves the file as it is. Do not add a memory fallback for an unreadable box: its data would be lost when the session ends.

### O. End-to-End Encryption (E2EE) Architecture (Track E)
- **Scope & Platform Invariant**: E2EE is enabled for 1-to-1 chats on native mobile platforms (`!kIsWeb && (Platform.isAndroid || Platform.isIOS)`).
